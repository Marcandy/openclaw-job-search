# Autonomous daily applications

The daily controller runs inside OpenClaw's native command scheduler. It does not need a Codex chat, an agent to launch a browser script, or a new approval for each batch. A private standing policy records the user's instruction and pins the code, configuration, confirmed facts, resume bytes and discovery inputs. The existing exact-manifest workflow remains available for manually approved campaigns.

Run at 12:30 America/New_York every day, including weekends, with a 16:30 catch-up. Both runs share one SQLite worker lock and a twelve-application daily limit. Manual applications and possible unconfirmed deliveries also consume the day's limit. A second run exits when the target is already met. Unknown personal facts, new legal consent, accounts and visible CAPTCHA cause a skip; the controller selects another eligible role. It never retries a submitted or uncertain destination.

No employer receives more than two applications in one New York day. Its recruiters see every application under one name, and a burst of unrelated roles reads as indiscriminate. Submitted and uncertain deliveries count toward this cap; a proven pre-delivery block does not. Set `autonomous.maxApplicationsPerCompanyPerDay` in the private configuration to change it. The cap applies to requested extra batches too.

The target means twelve confirmed submissions, not twelve attempts. Each posting has a five-minute browser deadline. Blocked forms and known pre-delivery failures do not consume the target: the replacement queue tries other eligible roles. When it exhausts the current pool, it researches more employers and continues in the same run. Research runs only when existing candidates are exhausted, with at most three batches of twenty employers per run, a seven-day research-attempt cache, and a seventy-minute overall budget. The catch-up run shares the same daily count. Exhausted supply, time limits and held deliveries appear explicitly in the report; twelve successful applications cannot be guaranteed regardless of conditions.

Discovery reads fresh official employer boards. Existing location, title, experience, compensation, company and blocker gates still apply. Cached company evidence expires after 30 days. When the pool needs more evidence, the controller asks OpenClaw for public company research using an explicit supported model; it checks the returned source excerpts before caching them. Ordinary discovery and submission use no model tokens. Free-text application answers use a pinned resume-summary template, not unrestricted generated claims.

Daily discovery and browser submission support Ashby, Greenhouse and Lever. Lever discovery uses public postings; its hosted application form remains authoritative for custom questions. Required custom labels, native choices, selected location and accepted resume bytes are checked before Submit. An interactive CAPTCHA still causes a skip.

Run `node tools/audit-boards.mjs` to inspect the board registry, or add `--apply` to save the audit and a backup. Valid dotted and encoded-space board names are accepted. Confirmed missing boards (404/410) and invalid entries are quarantined; transient failures never disable a board. An audit checks quarantined boards too and reactivates those that recover. Scheduled discovery excludes quarantined entries instead of repeatedly fetching known missing endpoints.

Company verification shares a seven-day SQLite source-document cache. Cheerio extracts HTML text and published structured data without running page scripts. PDF.js extracts PDF text in a time- and memory-limited worker, with page references, a five-megabyte input limit and at most fifty pages per document. Scanned documents without text remain unsupported. Cache entries retain the source URL, original-byte hash, fetch time and parser version; failed requests never replace a good cached snapshot. Headcount bounds, dated signals and exact corroborating excerpts remain required. HTML/PDF parsing uses no model tokens.

When a cited site refuses a plain request (HTTP 401, 403, 429 or 503), serves an empty app shell, or builds the quoted text with JavaScript, the source is read once more by headless Chrome in a throwaway context. It visits public HTTPS addresses only, holds no applicant data and never interacts with a challenge page. The rendered text is cached like any other source, and excerpts must still match it exactly. Sites that block every automated browser, and quotes that are not on the page, still fail verification.

The board registry can grow from an open-source JobSpy sweep. Run `python discovery/discover.py --all-cities --json sweep.json`, then `node tools/harvest-boards.mjs sweep.json` to list the Greenhouse, Lever and Ashby boards behind the sweep's employer links. Each new board is fetched through its public API and kept only when it lists a software role in an approved city; `--apply` adds them with a backup. Changing the registry changes the pinned boards hash, so renew the standing policy afterwards. Aggregator links remain discovery-only.

Before every submission, the controller writes an exact expiring manifest and records its standing-policy authorization. It checks live labels and required controls, including hidden Ashby Yes/No inputs, uploads the approved resume bytes, verifies entered values, then checks the policy again. It counts success only after an observed official ATS confirmation with the form gone and a saved screenshot. An ambiguous result is held and consumes a slot. A process crash is recovered only when the controller can identify its own dead process; possible deliveries remain held.

A CAPTCHA appearing after Submit is a replaceable failure when no possible application write was observed and the page has been closed to stop delayed delivery. Known Google reCAPTCHA transport endpoints are excluded from application writes; the worker must still observe an unfinished challenge. Other writes, including cross-origin writes and lookalike CAPTCHA hosts, without a receipt remain uncertain. Such a delivery is never reported as successful or blindly replaced past the daily cap.

JavaScript modules use Prettier with a pinned development dependency. Run `npm run format` before committing and `npm run format:check` to verify; CI enforces the same check. The replacement queue is a separate module so its completion and exhaustion behavior can be reviewed and tested independently of live applications.

Private deployment files under the runtime root:

- `autonomous.config.json`: the selected search profile and runtime paths.
- `autonomous-policy.json`: revocable standing authorization, twelve/day, pinned inputs, supported location choices and an approved application-summary template.
- `autonomous-company-profiles.json`: previously verified company evidence with verification dates.
- `daily-latest.json` and `daily/YYYY-MM-DD/report.json`: counts, receipts, skips, errors and shortfalls.

Each report explains a shortfall in three read-only fields. `factGaps` ranks the questions that blocked roles, grouped across employers, so one decision can unlock several applications. `poolFunnel` counts why each discovered role missed the pool: city, already applied, company cap, missing company profile, the first failed role check, or a company that is not primary-eligible. `researchSkipped` says why no research ran; when no employer is left to research, it counts household names, employers already profiled and those researched within seven days. None of these fields change selection or answers.

Routine answers cover common wording variants only when a confirmed fact supports them: legal first and last name, most recent company, where you first heard about the role, U.S. or Americas residence, a listed set of states (from the confirmed home state), country lists and clearance status. A choice question still needs an exactly offered option. Recent job title, privacy acknowledgments and recording consent remain blocked until the user supplies an answer or a standing decision.

Run `node tools/daily-run.mjs --config <private-config> --runtime <runtime>` for the actual controller. `--preflight-only --max-preflight 2 --no-research` checks public forms without entering applicant data or submitting. The application controller never imports its exported CSV; SQLite remains authoritative.

For an explicit additional batch, `node tools/start-application-batch.mjs --count 15 --cli <openclaw.mjs> --instruction-file <user-request.txt>` creates a separate private, date-limited grant and a one-time native OpenClaw command job. It records the initial occupied slots and caps additional possible deliveries at the requested count. The standing twelve-per-day policy remains unchanged. A dated grant fails after its New York campaign date. Company research excludes employers already barred by the household-name rule before spending model tokens.

Only when the user explicitly permits older verified-open postings, add `--allow-verified-open-older`. This creates a separate batch configuration: older postings must have same-day employer confirmation, dated in the campaign timezone. It does not change the standing posting-age rule. Mechanical, manufacturing and hardware titles are excluded before form inspection. So are developer-relations, go-to-market, technical-support, sales and solutions titles: they contain "engineer" or "developer" but are not the targeted software work. An unfinished Greenhouse email-verification gate is replaceable only when the official instruction, eight empty code controls and disabled final Submit establish that submission is still blocked; the worker never reads or enters a verification code itself.

## Greenhouse emailed-code gate

Some Greenhouse employers email an eight-character code after the first Submit and accept the application only once it is typed in. The code proves a person is present, so OpenClaw never reads the mailbox for it. With `verificationCodeEntry.enabled` in the standing policy and a visible browser, the run keeps the filled page open, brings Chrome to the front and shows a Windows notification. The applicant types the code; once all eight boxes hold a code that has stopped changing, OpenClaw presses Submit, and a rejected code can be retyped. Success still requires the ATS confirmation and screenshot.

A wait lasts up to `maxWaitMinutes` (default 10) per posting and `maxRunWaitMinutes` (default 20) per run, and never runs past 75 minutes into the run. After one missed code, later gates in that run skip the wait. A wait that ends with Submit never pressed and no write after the gate releases the slot, including when the applicant closed the page. Once OpenClaw has pressed Submit with a code, an unconfirmed result is held as uncertain like any other.

Every gate stop verified as not sent goes on a manual-completion list in the runtime root: `manual-completion.json` and the readable `manual-completion.md`. Each entry has the posting link, the resume to use and the answers OpenClaw had filled, newest first. The run report lists them under `manualCompletion`, and a notification at the end of the run names the file. OpenClaw never retries a listed posting. Without the policy setting, gate stops still go on the list.

```json
"verificationCodeEntry": { "enabled": true, "maxWaitMinutes": 10, "maxRunWaitMinutes": 20 }
```

Use `tools/install-daily-schedule.mjs --cli <installed-openclaw.mjs>` to preview replacing the legacy research schedule; add `--apply` to install and verify readback. Backups of the old schedule remain private. Disable the OpenClaw job or set the private policy's `enabled` to false to stop future submissions. Code, config, resume or confirmed-fact changes require deliberate policy renewal; a changed hash stops execution.

The Windows gateway must be available on this computer. A logon trigger and a wake/start check before each run can restore it after sleep or restart. The wake task's "Wake the computer to run this task" setting does nothing unless the power plan allows wake timers. Windows often defaults to "Important Wake Timers Only" on AC power, which ignores Task Scheduler. Enable them with `powercfg /setacvalueindex SCHEME_CURRENT SUB_SLEEP RTCWAKE 1` followed by `powercfg /setactive SCHEME_CURRENT`, and confirm with `powercfg /waketimers` while the machine is awake. Battery wake (`setdcvalueindex`) is left to the owner, since it can wake a laptop inside a bag. A powered-off or signed-out computer cannot run an interactive browser. If eligible roles or supported forms run short, the report records the actual shortfall; it never invents applications to reach twelve.
